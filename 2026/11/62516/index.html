前言

Gitea 接入 LDAP 后，用身份中心的用户名和 Gitea 原用户名都能进入同一个账号。刚接入时这很方便，时间久了却容易忘记客户端里存的是哪个名字。若直接改 Gitea 用户名，个人仓库的地址也要跟着核对。我最后保留了原仓库所有者，在 Authentik 原用户上统一登录名，再逐个调整依赖旧名字的应用。

以下用 old-login 表示旧登录名，repo-owner 表示统一后的名字，Gitea 原账号写作 Repo-Owner。大小写差异保留下来，便于区分仓库所有者与目录登录名。

一、改名前的账号清单

服务 需要记下的值 迁移后用什么判断还是原账号
Authentik 用户 UID、用户名、组、各 OIDC Provider 的 Subject mode UID 和组成员关系
Gitea 本地用户 ID、仓库所有者、LDAP 登录名、关联的 OIDC 源 同一用户能管理原仓库，已有 remote 可继续使用
Jellyfin 用户 ID、用户名、SSO 源的 CanonicalLinks 同一用户能看到原观看记录和收藏
Navidrome 用户 ID、用户名、管理员标记 网页回到原音乐库，客户端仍能访问
Nexus LDAP 登录属性、外部组与角色映射 新登录名可见原有仓库及相应权限

先在 Authentik 搜索目标名，同时检查各应用有没有同名的新账号。若已存在两个实际用户，应先确认归属再处理。显示名称只是界面上的昵称，改昵称不能替代这次登录名迁移。

我保留了一个可用的管理员会话，并备份 Authentik 数据库、Gitea dump、Jellyfin 用户及 SSO 插件配置、Navidrome 数据库。另记下各应用中原用户的 ID。改名后若只能看到一个空媒体库，拿 ID 比对比看头像和昵称可靠。

二、在 Authentik 原用户上改名

打开“目录 → 用户”，选择原账号进入编辑，将用户名从 old-login 改为 repo-owner，保留原密码、昵称和组成员。重新打开同一条用户记录，核对 UID，并用无痕窗口验证新名能登录身份中心。

改名前还需要打开关联应用的 OAuth2/OIDC Provider 核对 Subject mode。本次使用基于用户 ID 的 hashed_user_id，因此原地改名能保留同一 Provider 下的 OIDC 主体标识。若自己的 Provider 用用户名生成 sub，应先按应用的旧账号关联方式另作迁移。即使 sub 稳定，应用也可能另存一份用户名索引，Jellyfin 就需要单独处理。

LDAP 侧按新名称查询 cn，再查一次旧名称。使用各 Provider 自己的 Base DN。查询新名应命中原用户，旧名应退出日常认证路径。最后检查表达式策略和属性映射中有无直接写入的旧用户名。

三、Gitea 保留仓库所有者

我保留 Gitea 用户 Repo-Owner、用户 ID 和个人仓库路径。以 Gitea 管理员打开“站点管理 → 用户账号”，找到 Repo-Owner 并点编辑。保留“用户名”和现有 LDAP 认证源，把“外部登录名”（login_name）从 old-login 改为 repo-owner，保存后重新打开同一用户核对。若通过管理 API 更新，先读回原用户及来源 ID，再提交，避免误选同名的 OIDC 来源。

第五篇为不同用户名设置的 giteaUsername 继续指向原 Gitea 名称。在个人设置的“安全 → 关联账号”核对原 OIDC 关联仍在。分别退出并用 LDAP 密码、OIDC 按钮重新登录，各打开同一个已有仓库，再检查仓库设置是否可用。这次工作区里的 Git remote 沿用原地址。Gitea 的账号关联与 LDAP 配置

四、Jellyfin、Navidrome 与 Nexus

Jellyfin。 在管理后台的用户列表中修改原用户的名称，或通过原生用户 API 更新同一用户 ID。在第九篇第 5.2 节列出的 SSO 插件配置接口读取完整配置并备份。在对应认证源的 CanonicalLinks 找到键 old-login，确认值是原用户 ID、目标键 repo-owner 尚未占用，再将键改为 repo-owner。通过同一接口保存完整配置，重新读取并比对这条映射。保留 LDAP 的 UID 映射和用户原有的认证提供者。用新名加密码登录一次，退出后点 OIDC 登录，再打开一部有播放进度的影片。我用这两条路径都回到了原媒体账号。Jellyfin 双认证配置

Navidrome。 在原用户上更新用户名，保留用户 ID、本地密码和管理员属性。网页经代理认证后，以新名进入原音乐库。音乐客户端若还保存旧名，需要单独修改服务器连接中的用户名，密码仍是 Navidrome 原有密码。此次还用新名加原密码调用 API，返回了改名前的同一用户 ID。Navidrome 网页与音乐客户端

Nexus。 LDAP Realm 按 cn 解析用户。保留原组与外部角色映射，在 Nexus 自己的登录框输入新名和 Authentik 密码，核对仓库和管理设置。Nexus 本地的应急管理员单独保留。Nexus LDAP 角色映射

五、验收与回退

我最后用新会话逐项验证：Gitea 的 LDAP 和 OIDC 都回到原仓库所有者；Jellyfin 两种方式都保留观看记录；Navidrome 网页显示原音乐库；Nexus 接受新用户名并保留原权限。对于按稳定主体关联的应用，保留旧绑定并用原数据核对归属，比重新打开自动注册更容易发现问题。

如果某个应用进入了新建的空账号，先停止用该账号产生业务数据，记下新旧 ID。从出问题的应用开始回退原登录名和映射。例如 Jellyfin 需要一起恢复用户名与 CanonicalLinks，Gitea 只需恢复原 LDAP 登录名。整库备份留作最后手段，优先原地修复，避免覆盖改名后新增的提交和观看记录。

还有一类名字不在这次个人身份迁移里：代理向 qBittorrent、AdGuard Home 转发的后台账号，以及用于 LDAP 查询的服务账号。它们有独立的凭据和轮换周期。个人用户改名后若只有某个共享后台进不去，先看 Proxy Provider 引用的组属性。
